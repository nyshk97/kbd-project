# 意思決定の記録

## プロジェクト目的：自分用の最高のキーボード

- このプロジェクトは自分用の最高のキーボードを作ることを目的にする
- 量産・販売・第三者向けキット化は目的にしない
- 一般的な使いやすさより、自分の手・作業環境・好みに合うことを優先する
- 部品単価、入手性、製造容易性は考慮するが、量産時の原価最適化やサプライチェーン安定性は優先しない
- 販売向けの認証、パッケージング、ユーザー向け組み立て性、販売後サポートのための設計は対象外にする
- BLE無線モジュールの使用地ごとの法令適合は、販売有無と別に部品選定時に確認する

## 進め方：段階試作

- 最終形を一度で作らず、簡単な試作を複数台作って段階的に近づける
- 各試作機は `boards/pXX-*` に分け、目的・部品表・作業ログを個別に持つ
- 最終形の設計データは `target/` に置き、試作で検証できた要素だけを反映する
- まだ使わないディレクトリは先に作らず、必要になった時点で追加する
- 試作をまたいで使うZMK設定、Ergogen定義、footprint、ケース部品が出てきたら `shared/` を作る

## スイッチ：p01はChoc v1 Red、targetはChoc V2（19mmピッチ）

- 旧方針はChoc v1 Red（ロープロ最薄・Macの打鍵感に最も近い）だったが、Auto-KDKがChoc v1非対応のため覆した（2026-07-15）
- targetはChoc V2・19mmピッチ。MacBookのキーピッチ（約19mm）を維持して運指の記憶を移行する
- Choc V2はトータルトラベル約3.2mm（バリアントにより2.8mm）・アクチュエーション約1.3mmで、ロープロ最短クラス。MacBook（約1mm）の完全再現ではなく「メカニカルで到達できる最良の近似」と割り切る
- 軸（バリアント）はPCB・ケース設計に影響しないため後から決める。MacBook近似の観点で軽めリニア（Deep Sea Mini Pink Island 35gf / Islet 43gf / Red 45gf前後）を打ち比べ候補にする
- **軸は Kailh Deep Sea Silent MINI Islet（43gf 静音リニア）に決定（2026-08-04）**。YUZUキーキャップ到着後、p02実機にキーキャップ込みで挿して打ち比べた結果 Islet が最良（遊舎工房商品名「Kailh Deep Sea Low Profile Choc V2 サイレントスイッチ 1353 RGB MINI」のIsletバリアント）。~~2026-08-02にキーキャップなしの素のPCB打鍵で Pink Island（35gf）に決定~~ したが、キーキャップの質量が乗ると評価が逆転した（結果的に2026-07-15の当初本命Isletに戻った）。**軸の評価は素のステム打鍵では決まらない。必ずキーキャップを装着して打ち比べる**。「43gf前後の軽めロープロ静音リニアが好み」という知見はステム規格に依存しないため、完成版でMX規格に変えることになっても同等品を指名買いできる
- Choc V2はMXステム。キーキャップ自作はフラット・薄型・広めを狙うとMacBook感が出る
- Choc v1とV2は物理非互換（PCBセンター穴径が違う）ため、p01のPCBにV2は刺さらない。ホットスワップソケット自体は共通で、p01のソケット検品知見は活きる
- 2U以上のキーにはスタビライザーが必要。Choc V2対応ロープロスタビの入手性を確認し、入手困難なら2U以上のキーを置かないレイアウト（親指2Uを分割等）に逃がす

## PCB・ケース設計方針：Auto-KDK

- 旧方針（Ergogen + FreeRouting + KiCad のフルスクラッチ）を覆し、targetはAuto-KDK（sekigon-gonnoc氏のWebツール https://auto-kdk.pages.dev/ ）で設計する（2026-07-15に調査のうえ決定）
- 決定理由: レイアウト指定からPCB（EasyEDA形式json→JLCPCB発注）・ケースSTL・ZMK shield一式（ZMK Studio対応）・フォームカットSVGまで自動生成でき、要件（分割・無線ZMK・ロースタッガード・トラックボール）をネイティブに満たす。特にケース設計の学習コストを丸ごと消せる
- 2026年6月ビルド（ver 2026-06-03）が稼働中のアクティブなプロジェクト。製造到達したユーザー事例も複数あり
- 制約として受け入れたもの:
  - 専用コントローラボード必須（XIAO等の市販MCUボードは選べない）
  - 無線はrow+col合計18ピン上限。トラックボール使用側は実質14ピンで、5行×9列だと上限ちょうど（キー追加不可）
  - PCBデータはEasyEDA形式のためKiCadでの手直し不可。手直しはEasyEDA上で行う
- 未解決事項の確認結果（2026-07-15、データ生成zipで確認）:
  - ライセンス: 解決。利用規約により個人利用・商用利用とも可。ただし生成データは**Auto-KDK公式コントローラとの組み合わせでのみ使用可**。現状有姿・無保証
  - ホットスワップ: 解決。生成PCBにKailh Chocソケット（CPG135001S30）×64 + 1N4148W×64のフットプリントあり。はんだ付けは自分で行う
  - 左手PCB: 解決。left/right/panelized（面付け版）の3種のEasyEDA jsonが生成される
  - スタビライザー: フットプリントなしと判明。Choc V2構成では2U/2.25Uキー（左Shift 2.25U・左親指2U・右2U・右Enter 2.25U）がスタビなしになる → **スタビなしのまま行くと決定（2026-07-15）**。ロープロ＋トラベル3mm＋軽量キャップなら実害は小さい見込みで、「スタビなし幅広キーが実用になるか」自体をp02の検証項目にする。ダメなら次イテレーションで幅広キーを1.5U以下に分割（既存マトリクスの空きセルに収まるためピン数制約には抵触しない）
  - ドングル対応: 解決。zmk-config-split-us60pctのdongleブランチで、dongle shield（central役・モックkscan）＋right_p shield（右手peripheral化・トラックボールをzmk,input-splitで中継）を追加し、akdk_bt1ドングル/XIAOドングル（ZMK v0.3では board名 `seeeduino_xiao_ble`。`xiao_ble//zmk` は新しいZMK mainの名前でv0.3では無効）とも全ターゲットビルド成功（2026-07-15）。必要になったらこのブランチをmainに取り込むだけ
  - 自動配線の品質: 未検証（EasyEDAインポート時に確認）
- 旧方針のErgogen成果物（キー配置・1:1印刷アウトライン）とKLE基準は、レイアウト検討の参考資料として残す

## キーマップ：トラックパッドジェスチャの代替はZMKコンボ

> **完成版では不要になる見込み（2026-08-02）**: Magic Trackpadをケースにはめ込む方針にしたため、macOSのジェスチャーがそのまま使える。下記のコンボはp02（トラックパッドなし構成）でのみ意味を持つ。


- トラックパッド廃止に伴い、4本指スワイプ相当の操作はmacOS標準ショートカット（Ctrl+矢印）をコンボで送る（2026-07-15）
  - J+K = Ctrl+←（左のスペースへ）
  - K+L = Ctrl+→（右のスペースへ）
  - J+K+L = Ctrl+↑（Mission Control。トグルなので閉じるのも同じコンボ）
- Ctrl+↓（App Exposé）は不要と判断。恋しくなったらM+,+.（JKLの真下段）に追加する
- 誤発動対策はrequire-prior-idle、3キー同時が押しにくければtimeout-msを50→80ms程度に調整
- コンボはZMK Studioでは編集できないため`.keymap`に記述してGitHub Actionsでビルドする。レイヤー・キー割り当ての試行錯誤はStudio、確定したコンボはkeymap、という分担

## 完成版の方向性（2026-08-02 更新）

p02を組み上げた経験を踏まえた、完成版の要件イメージ。まだ設計に入る前の方向性であり確定ではない。

### 前提の裏付け：Nuio Flow + Magic Trackpad の実運用経験（2026-08-03 記録）

**「分割キーボードの中央にトラックパッド」という配置は、すでに実運用で検証済み**だった。以前 Nuio Flow（マグネットのデスクパッド上に分割キーボードとトラックパッドを配置するシステム。キーボード$400〜、フルセット$1,000超）と自前の Magic Trackpad を組み合わせて使っていた。

現在は使っておらず手放しているが、**その理由は配置への不満ではなく、周辺の運用への不満だった**：

| 手放した理由 | p03での扱い |
|---|---|
| Nuioの接続が不安定だった | Nuio固有の問題。自作＋ZMKなら自分で制御でき、ドングル構成のビルド検証も済んでいる |
| 充電の管理が面倒だった | **乾電池案（案B）が直接の回答**（下記「薄型化・電源方式」参照。この経験により案Bを本命に格上げ） |
| 机の上にPCの他にキーボード左右＋トラックパッドの3つが増えてごちゃつく | **一体化ケースが直接の回答**。3個バラバラより机がすっきりするという期待がp03の動機そのもの |

**この経験は「トラックパッドを中央に置く配置が自分に合うか」というp03最大の前提リスクを潰している。** 配置は気に入っていて、嫌だったのは接続・充電・散らかりの3点。p03はその3点すべてに設計上の回答を持っている。

なお `docs/decisions.md` の「トラックボールセンサー」の項に「p02でトラックボールを実地評価できなかったため比較材料がない状態での判断」と書いたが、**トラックパッド側については比較材料がないどころか一次の実運用データがある**、と補正する。未評価なのはトラックボールの側。

### 外部キーボードの重要度が上がった（2026-08-03）

Nuio運用時は Mac 1台（MacBook）だけだったが、現在は**自分のMacBook・案件で支給されたMacBook**の2台で、さらに**常時稼働のmac miniを追加予定**。複数台を1組の入力デバイスで扱う必要が出たため、外部キーボードの重要度が当時より上がっている。この変化は下記「複数Mac運用とデバイス切り替え」の論点を生む。

- **トラックパッド + キーボードが一体で綺麗に収まるケース**を自作する。ポインティングデバイスはトラックボールからトラックパッドへ変更を検討（p02でトラックボールを実地評価できなかったため、比較材料がない状態での判断である点は認識しておく）
- **3Dプリンターを導入**してケースを内製する。動機は、p02でJLC3DPに外注したケースが「思ったよりゴツい」と実物で分かったこと。外注は1回$155＋納期がかかり試行回数を稼げないため、手元で回せるようにする
- **左右分割・電池駆動・薄型**は維持（下記「薄型化・電源方式」の検討メモを参照）
- p02で使えたChocソケットのはんだ付け・PCB/PCBA発注・コンスルー接続は、もうハードルではないという自己評価（実績: 128箇所で不良の疑い1箇所のみ）

### 完成版で新たに越える必要があるハードル（3Dプリント技術以外、2026-08-02整理）

### 中央トラックパッド統合ケースの設計メモ（2026-07-30 検討、未確定）

- 奥の縁にUSB-Cポート＋電源スイッチの逃げ、取り出し用の指掛かり穴を設ける
- 質感の分担: 外装の最終版はJLC3DP SLA（Black Resin）、試行錯誤・土台類は自宅FDM（256mm級ベッドで全パーツ印刷可）

### 決定的な論点：乾電池と充電回路の衝突

**A・B・C はいずれもLi-Po用の充電回路を内蔵している。** 乾電池を繋ぐとUSB接続時に充電ICがエネループへリチウム用の充電プロファイルを流すことになり危険。さらに電圧の成立性も既製ボードでは保証されない:

| | 給電経路 | 2.4Vで成立するか |
|---|---|---|
| A | PHコネクタ → 充電IC → ? | **回路図が非公開**。LDOが入っていればドロップアウトで不安定。確認手段が実測しかない |
| B/C | BAT端子 → 充電IC(BQ25101) → LDO → 3V3 | BAT端子は使えない。3V3ピンへの直接給電なら動く可能性があるが、電源回路への逆流とスリープ時消費電流が懸念 |
| **D** | **電池 → モジュールのVDD 直結** | **○ レギュレータも充電ICも載せない設計にできる。変換ロスゼロ** |

エネループ2本は満充電2.8V→公称2.4V→終止2.0Vで、nRF52840の動作範囲（1.7〜3.6V）に全域が収まる。問題はチップの手前の電源回路であり、A〜Cは「他人が設計した電源回路に想定外の電圧源を横から突っ込む」形になる。**乾電池を要件に据えるならDに一本化される。**

昇圧IC（2.4V→3.3V）でA〜Cを生かす逃げ道はあるが、常時待機電流を食い無線の省電力と相性が悪いため勧めない。Dなら昇圧そのものが不要。

### D（MDBT50Q）のアンテナ設計は、当初評価より容易

キープアウトの実要件はシンプルで、**アンテナの真下と周辺にグランド・配線・電源プレーンを置かない**（多層基板なら該当領域から全レイヤーのベタを抜く）こと。データシートの表現は "No ground pad should be included in the corresponding position of the antenna. The No-Ground-Pad area should be as wide as you can."

失敗リスクを発注前に潰す手段が3つある:

1. **Raytacが無料でレイアウトレビューをしてくれる**。データシートに、レイアウトをPDFで `service@raytac.com` に送ればアンテナ設計要件への適合をチェックする旨が明記されている。JLC3DPのReview Before Paymentと同じ構図で、既に経験済みの進め方
2. **公開リファレンス設計がある**: `siderakb/mdbt-micro`（MDBT50Q使用のnRFMicro/ProMicro互換ボード）、ErgoSNM（MDBT50Q使用のキーボード）、Skean（E73 nRF52833の完全無線分割キーボード）。アンテナ周辺のレイアウトを実績のある設計から写せる
3. **この構成は干渉源から離しやすい**（下記）

### 本構成での電波干渉の評価

| 干渉源 | 評価 |
|---|---|
| 乾電池（エネループ単3×2）＝金属の塊 | **回避可能**。案Bは電池を後端配置のため、MCUを前端に置けば最も離れる |
| Magic Trackpad＝アルミ筐体が中央にある | **回避可能**。左右それぞれのMCUを**外周側**に置きアンテナを外に向ければ最も遠くなる |
| 3Dプリント樹脂ケース | 問題なし（電波を通す）。ただし薄型化で**金属補強板を入れる場合はアンテナ付近を避ける** |

**「MCUを外周側・前寄り、電池を後端」**という配置ひとつで2つの干渉源から同時に離れる。USB-Cポートも外側に来るが、充電・書き込み用なので支障ない。

**残る懸念は左右間通信（central ⇄ peripheral）が中央のアルミ板で遮られないか**。ただし①BLE 2.4GHzは回折・反射し距離160mmは近すぎるほど近い（到達距離は10m級）②先行例のNakaniwaが製品として成立している ③**ドングル構成にすれば左右がそれぞれドングルと通信する形になり、この問題自体が消える**（ビルド検証済み）。

## 複数Mac運用とデバイス切り替え（方針決定 2026-08-03、実機検証は未実施）

**Mac 3台（自分のMacBook / 案件支給MacBook / 導入予定のmac mini）を1組の入力デバイスで扱う**という要件が新たに判明した。ここに、中央トラックパッド構成に固有の問題がある。

**Magic Trackpadは独立したBLEデバイスなので、キーボードと連動して切り替わらない。**

- キーボード（ZMK）は `BT_SEL 0-4` で5台まで一発切り替えできる（p02のキーマップに実装済み）
- Magic Trackpadには切り替えボタンがなく、**macOSのBluetooth設定から手動で繋ぎ直すしかない**
- 結果、「キーボードはmac miniに、トラックパッドは案件MacBookに繋がったまま」という状態が日常的に起きる
- **一体型ケースにすると見た目は1つのデバイスなのに、中身は独立した2デバイス**というギャップがここで露出する

これは「Magic Trackpadを使う＝ZMK側は一切関与しない」という利点（ドライバ・電圧・基板実装のハードルが消える）の裏返しで、トレードオフとして受け入れた構造から出てくる問題。

### 解決方針：blueutil + ホットキー + ZMKマクロによるソフトウェア切り替え（本命 2026-08-03）

**成立を確認した前提2つ:**

- **Magic Trackpadは複数のMacとペアリング情報を保持できる**（同時接続は1台のみ）。切り替えのたびに再ペアリングする必要がなく、接続/切断を叩くだけで切り替わる。※「1ホストしか記憶しない」であればこの方針は不成立だったため、実機入手後に最初に確認する項目にする
- **`blueutil` でデバイスアドレス指定の接続/切断ができる**（`blueutil --connect <addr>` / `--disconnect <addr>` / `--paired` でアドレス取得）。Homebrewで入る単一バイナリ

**構成:**

1. Mac 3台に `blueutil` と「トラックパッドを自分に接続するスクリプト」を置く
2. Hammerspoon か Karabiner でホットキーに割り当てる
3. キーボードを `BT_SEL n` で切り替え → 切り替え先Macでホットキーを押す → トラックパッドがそのMacに来る
4. さらに **ZMKのマクロで1キーに統合できる**: `&bt BT_SEL n` → `&macro_wait_time`（BLE再接続を待つ）→ ホットキー送出。**キー1つでキーボードとトラックパッドが揃って移動する**という理想形になる

常駐エージェントの自作すら不要で、実質「スクリプト1本＋ホットキー登録」で済む。

**クリア済みの前提（2026-08-03 確認）:**

- ✅ **案件支給MacBookにツールを置ける**（MDM制限は問題にならない）
- ✅ **切り替え先Macがスリープ中は動かない**問題は許容できる

**残るリスクと対処:**

- Magic Trackpadは「近くにある最初のペアリング済みMac」に繋がる挙動があるため、どこにも接続していない状態から復帰するとき意図しないMacに奪われる可能性がある。各Macのスクリプトに「非アクティブ時は掴まない／掴んだら離す」ロジックを持たせて対処する
- macOS 12以降のBluetooth TCC権限のプロンプト挙動は実機で確認する

**この方針がケース設計に与える帰結（重要）:**

- **トラックパッドを有線USB-Cで運用する必要がなくなる → ケース内のUSB-Cケーブル取り回しの設計が不要**になる。必要な開口はトラックパッドの充電ポートと電源スイッチの逃げのみ
- **机の上に切替器などの物理デバイスが増えない**。「3個バラバラでごちゃつくのが嫌」というp03の動機と正面から整合する
- キーボードをドングル構成にするかは、この方針とは独立に判断してよい（BLE直結のまま `BT_SEL` で運用できる）

**検証のタイミング**: この方針は**3Dプリンターより先に、Magic Trackpadを買った時点で検証できる**。ケース不要、手持ちのMac 2台で完結する。¥2万の出費だけでp03の運用面リスクが潰せるため、購入後の最優先タスクにする。

### 見送った案（2026-08-03）

- **mac miniをホストに固定**して入力デバイスは常時mac miniに接続、他Macへは画面共有で入る。案件作業の常用に耐えるか不明なため見送り
- **Universal Control**: 同一Apple IDが必須のため、案件支給MacBookでは使えない公算が高い（管理プロファイル）
- **トラックパッドを有線USB-Cで運用 ＋ キーボードをドングル構成**にし、ケーブル1本とドングル1個の挿し替え（またはUSB切替器でワンボタン化）で両方同時に切り替える。ソフトウェア切り替えが成立するなら、机上に物が増えるこの案を採る理由がない。**ソフト案が実機検証で崩れた場合のフォールバックとして残す**（その場合はケース内のケーブル取り回しの設計が必要になる）
  - なお、ドングル構成自体はビルド検証済み（zmk-config-split-us60pctのdongleブランチ、2026-07-15）なので、フォールバックに倒してもファームウェア側の追加ハードルはない

## 完成版の薄型化・電源方式（検討メモ、未決定 2026-07-29）

p02実物のケースが想定よりゴツかった（高さがある）ことを受けた、完成版フルスクラッチ設計に向けた検討メモ。判断はp02を組んで運用してから。

- 高さの内訳: 「チルト＋テント」と「PCB下の部品スタック」が主因。スタックはコンスルー2.5mm＋コントローラ基板1.6mm＋モジュール約2mm≒約6mmと、バッテリー5mm厚（DTP502535）の同居
- Auto-KDK枠内での調整余地（ケース再生成＋再印刷のみで可能）: チルト5°→4.1°（ツールの下限、後端約-2.3mm）、テント4°→0°（片側約-10mm）、底面3mm→1.8mm（-1.2mm）。テント0°はMacBook近似とも整合するが、要否はp02の打鍵で体感してから
- **コントローラ直付け化**（無線モジュールをキーPCBに直接実装、コンスルー廃止）: 単体では約1mmしか薄くならない（律速がバッテリー5mmに移るため）。薄型バッテリーや配置変更とセットで2〜4mm。副次メリット: PCBA工場実装化・のぎけす屋供給依存の解消・コンスルー接触不良の根絶・1枚あたり¥2,000前後安い・USB/アンテナ配置の自由。デメリット: 充電IC等の周辺回路を自作に戻す・アンテナキープアウト失敗時はPCB再発注・修理性低下・ZMKボード定義の自作。技適はモジュール（Raytac MDBT50Q系等）の認証でカバー
- **電源方式：案B（乾電池・エネループ単4×2）に決定（2026-08-03）**。案Aは案Bが機構的に成立しなかった場合の代替として残す
  - **要件の性質**: 当初は薄型化の手段として案A/案Bを対等に並べていたが、Nuioを手放した理由のひとつが「充電の管理が面倒」という実運用の一次要件だったため格上げした。さらに実態を確認すると、**Nuioは1ヶ月に1回の充電で足りていたのに、残量を気にするのが嫌で前倒しでこまめに充電していた**。つまり**問題は充電回数ではなく「残量を気にする認知負荷」**であり、乾電池の本質的な利点は容量ではなく**切れたときの復旧が30秒で終わること**（予備を置いておけば、事前に気にする理由が原理的に消える）。この理解により、容量の絶対値の重要度は下がる
  - ⚠️ **Magic Trackpadは充電式なので「充電を一切気にしない」は達成できない**。ただし気にする対象が3つ（キーボード左右＋トラックパッド）から1つに減る
  - **単3ではなく単4×2を選択（2026-08-03）**。本人にこだわりがないため、容量より厚みを取る判断:

| | 直径（＝ケース厚みを直接決める） | 容量 | 重さ（2本） |
|---|---|---|---|
| 単3×2 | 14.5mm | 約2000mAh | 約54g |
| **単4×2（採用）** | **10.5mm** | 約750mAh | 約26g |

  - 決め手は**単4の10.5mmがMagic Trackpadの最厚部10.9mmとほぼ一致する**こと。これにより「トラックパッドと厚みを揃える」が努力目標から現実的な目標に変わる。容量750mAhも現行のDTP502535（約400mAh）の約2倍で、1ヶ月持っていた実績の2倍に相当。重さも半減するため「据え置き用途につき許容」という妥協が不要になる。エネループは単3も単4も1.2Vで、直列2本＝2.4Vは変わらない
  - 未検討: 電池ボックスを既製ホルダー（単4×2、¥100前後・接点設計不要）にするか、電池を直接抱えて金属接点だけ埋め込む自作にするか。薄型化を狙うなら後者だが、機構設計の手間と引き換え。設計着手時に決める
  - 案A: Li-Po薄型化（4mm厚の402535系300mAh前後）。現行の延長で最小変更。劣化懸念はPHコネクタ交換式（¥1,000前後で挿し替え）で実運用上は緩和されている
  - 案B（採用）: 乾電池（エネループ）を後端配置。キー面から電池が消えて前端8〜9mm級まで攻められ、後端の膨らみはチルト土手を兼ねる。Apple Wireless Keyboard A1314（単3×2の円筒＝足）が造形の前例。容量は単4×2=750mAh/単3×2=約2000mAhで現行の2〜5倍、充電回路不要・劣化と無縁。課題: トラックボールセンサーの電圧レール・重さ（単3×2で約50g増、据え置き用途につき許容と判断 2026-07-29）・エネループ運用前提（アルカリは液漏れリスク）・電池ボックスの機構設計（蓋・接点）
    - センサー電圧の調査結果（2026-07-29）: PAW3222の同族PAW3212のデータシートでは結線により1.7〜2.1V/2.1〜3.6Vの2構成があり、チップ自体は2.4V対応可能。のぎけす屋モジュール（sekigon-gonnoc/small-mouse-sensor-module）の公称は3.3V供給で回路図非公開のため、2.4V直結可否は未確定。確認手段: ①手元の現物に2.4Vを与えて実験（最確実）②作者にBOOTH等で質問 ③不可なら小型昇圧ICでセンサーのみ3.3V化（負荷0.27mAで影響は誤差レベル）。エネループ2本は満充電2.8V→終止2.0VでHigh Segment下限2.1Vとほぼ一致し、直結ならほぼ全容量を使える見込み
- **アルミケース**: 薄さへの寄与は小さい（肉厚分1.5〜2mmのみ、内部スタックは不変）。フルアルミはBluetooth遮蔽が問題で、樹脂窓かボトム樹脂が前提。スナップ→ネジ化の再設計必須、一点物4パーツで$400〜800級。折衷案はMJFナイロン（質感）やボトムプレートのみアルミ（重量感・剛性）
- **リポのコネクタ極性は統一されていない（2026-08-02に実地で判明）**: PHコネクタ（JST PH 2.0mm）には極性の業界標準がなく、セルのメーカーごとに赤黒の圧着位置が違う。p02で買ったDTP502535(PHR)はAuto-KDKコントローラと極性が逆で、そのままでは挿せなかった。回避策は①購入前に商品ページの写真で極性を確認 ②「セル単体＋コネクタ付きケーブル」を別々に買って自分で結線。**案Bの乾電池構成ではこの問題は原理的に起きない**（電池ホルダーは+側バネ/−側平板で極性が物理的に固定され、ホルダーからコネクタまでの配線も自分で作るため）。案Aの薄型リポを選ぶ場合は購入前の極性確認を手順に入れる
- p02運用で測ってから決めること: テント要否、電池持ちの実測（ZMKのBLE電池残量通知で記録）、質感の不満点の特定（軽さ・表面・たわみのどれか）
